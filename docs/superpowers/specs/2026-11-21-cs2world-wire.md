## 1. 握手与会话密钥

v0.0.1 在 UDP 上用一个往返建立会话。客户端发送 `ConnectRequest`，服务端验证后返回 `ConnectOK`。客户端验证响应并派生密钥，随后双方即可发送数据报。以下字段从零开始计数，区间 `[a,b)` 包含 a、不包含 b，LE / BE 分别表示小端和大端。PSK 取配置字符串的 UTF-8 字节。协议层直接使用这些字节，保留大小写和空白。

| 报文、方向 | 偏移 | 长度 | 字段及编码 |
|---|---|---:|---|
| ConnectRequest，客户端 → 服务端 | [0,1) | 1 | 标志 `01` |
| | [1,5) | 4 | `ClientTmpID`，随机 u32 LE，允许零 |
| | [5,37) | 32 | 客户端临时 X25519 原始公钥 |
| | [37,45) | 8 | Unix 时间戳，单位为秒，i64 BE |
| | [45,61) | 16 | 请求 HMAC-SHA256 的前 16 字节 |
| | [61,末尾) | Go 发送 87 | 随机填充。Go 固定发送 148 B，接收端要求至少 61 B |
| ConnectOK，服务端 → 客户端 | [0,1) | 1 | 标志 `03` |
| | [1,5) | 4 | `SessionConnID`，随机 u32 LE。Go 服务端将生成的零改为 1 |
| | [5,37) | 32 | 服务端临时 X25519 原始公钥 |
| | [37,53) | 16 | 响应 HMAC-SHA256 的前 16 字节 |
| | [53,末尾) | Go 发送 39 | 随机填充。Go 固定发送 92 B，接收端要求至少 53 B |

下列 `H(k,m)` 表示 HMAC-SHA256，参数依次为密钥、消息。双引号内的标签均为精确 ASCII 字节，`||` 表示原样拼接，`[:n]` 取摘要最前面的 n 个字节。

```text
ReqMAC = H("cs2world-hs-req:" || PSK, req[0:45])[:16]
OkMAC  = H("cs2world-hs-ok:"  || PSK, ok[0:37] || req[1:5] || req[5:37])[:16]

shared  = X25519(本端临时私钥, 对端32字节公钥)
prk     = H("cs2world-pfs-v0.0.1:" || PSK, shared || clientPub || serverPub)
aesKey  = H(prk, "aes-256-gcm-key")
c2sSalt = H(prk, "c2s-nonce-salt")[:4]
s2cSalt = H(prk, "s2c-nonce-salt")[:4]
```

两个方向共用 32 B AES 密钥。客户端发送和服务端接收使用 `c2sSalt`，反方向使用 `s2cSalt`。派生输入中的公钥顺序在两端均为客户端在前、服务端在后。展开步骤仅有上表三个标签，使用标准 HKDF-Expand 时自动追加的 `01` 会改变结果。Go ↔ Rust 向量应逐项比对 32 B 公钥、共享秘密、三个派生产物和握手标签。Rust 应拒绝全零共享秘密，按常量时间比较认证标签。

**时序与随机源。** Go 客户端为一次握手只生成一份请求和临时私钥，最多发三次相同的数据报。每次发送后读一个 UDP 数据报，读期限为 1,500 ms。超时、暂态 UDP 错误及无效响应都会消耗一次尝试。常规发送错误或非暂态读取错误立即结束。服务端先验证请求 MAC，再检查本地 Unix 秒与请求时间相差不超过 60 秒，含两端。合格的重复请求会产生新的服务端临时密钥、会话 ID 和响应。应答 MAC 绑定原请求的临时 ID 与公钥，两种握手报文的末尾填充均在 MAC 覆盖范围之外。

Go 的临时 X25519 密钥、临时 ID、会话 ID、两种握手填充以及第 2 节的数据报填充都来自 `crypto/rand`。整形器单独用 `math/rand` 采样目标包长，样本影响填充**长度**。Rust 对密码学字段和填充**内容**使用操作系统安全随机源，测试可注入固定时间、密钥及数据。跨实现无需产生相同的随机样本。

**互操作边界。** 分别用 Go 客户端与 Rust 服务端、Rust 客户端与 Go 服务端验证正常握手、错误 PSK、请求 MAC、错误绑定的响应 MAC、最小长度和填充改变。使用同一测试时钟重新签署偏差 −61、−60、+60、+61 秒的四个请求，预期依次为拒绝、接受、接受、拒绝。原 Go 测试将时间戳改为 120 秒前，随后沿用旧 MAC，单独执行该用例只能证明篡改会被拒绝。

源码依据为 `pkg/protocol/gns.go` 第 52–70、139–184、194–327 行，`pkg/transport/packet_conn.go` 第 69–123、202–219 行，`pkg/shaper/state_machine.go` 第 42–62、125–158 行，`pkg/protocol/gns_test.go` 第 11–49 行。

## 2. 数据报与接收状态

每个 `0x82` UDP 数据报封装一份来自 KCP 层的完整数据报，开启 FEC 时也可封装一个带 FEC 头的数据分片或校验分片。空载荷用于虚拟心跳。外层固定开销为 28 B，由 9 B 明文头、3 B 加密内头和 16 B GCM 标签构成。

| 层 | 偏移 | 长度 | 字段及编码 |
|---|---|---:|---|
| UDP 载荷 | [0,1) | 1 | 标志 `82` |
| | [1,5) | 4 | 握手分配的 `SessionConnID`，u32 LE |
| | [5,9) | 4 | 本方向的 `Seq`，u32 BE，首包为 1 |
| | [9,总长−16) | 可变 | AES-256-GCM 密文，包括内头、真实载荷及随机填充 |
| | [总长−16,总长) | 16 | GCM 认证标签 |
| 解密后，以明文起点为零 | [0,1) | 1 | 模式 `00` IdleDummy、`01` CombatTick、`02` FastDL |
| | [1,3) | 2 | 真实载荷长度 N，u16 BE |
| | [3,3+N) | N | 原始 KCP / FEC 数据报字节 |
| | [3+N,明文末尾) | 可为零 | 由安全随机源生成的填充，随密文一起认证 |

AAD 为未经修改的全部 9 B 外头。12 B nonce 为 `directionSalt[0:4] || LE32(SessionConnID) || BE32(Seq)`，接收端从会话状态和外头重建。每个发送方向有独立计数器，真实包、FEC 分片和虚拟心跳共用该方向的计数器。Go 发送长度先取整形目标与 `28 + N` 的较大值。当 `28 + N ≤ 1380` 时再将结果限制到 1380 B，原始载荷更大时保留完整载荷。Go 的 32 位计数器会自然回卷。Rust 应在发送序号耗尽前结束旧会话并重握手，保证同一密钥、方向和会话下 nonce 唯一。

| 接收状态或输入 | Go 参考行为与 Rust 互操作要求 |
|---|---|
| 服务端收到 UDP 数据报 | 先分流 A2S，再处理标志 `01` 且长度至少 61 B 的握手。其余数据报须满足 `82` 且长度至少 28 B，才能按明文会话 ID 找到接收密钥。 |
| 已知会话的加密包 | 核对外头和会话 ID，使用接收方向 nonce 和原头 AAD 验证并解密。认证通过后才允许更新重放窗口。 |
| 64 位滑动窗口 | 每会话接收方向维护最高序号和 64 位位图。拒绝零、重复值及落后最高序号至少 64 的值。落后 63 的未见值仍可接收。新最高值前移至少 64 时重置位图，只保留新包。 |
| 内部长度和通道 | Go 先登记已认证序号和活跃时间，再检查 `3 + N ≤ 明文长度`。解密成功且长度合法后，若模式为 `00` 或 N 为零，传输层计入虚拟包并消费。其余模式的非空载荷仅将前 N 字节交给 KCP，Go 对未知的非零模式也采用此规则。 |
| 地址与超时 | Go 服务端用会话 ID 查接收状态，用 UDP 源地址查发送状态。有效握手和成功打开的数据报都会更新地址映射。其接收缓冲区为 2,048 B。每 60 秒清理最后活跃时间早于“当前时间减 900 秒”的会话及地址项。 |
| 未知或无效输入 | 服务端对已知会话的重放静默丢弃。非 A2S 的无效握手、不可分流的包、未知会话、已知会话的认证或内长错误会触发 `ConnectionClosed`。已建会话的客户端对打不开的数据报继续读下一包。 |

拒绝报文为 `02 00 00 00 00 8B 13 00 00`，后接原因字符串的原始字节和一个终止字节 `00`。实际服务端分流路径使用 `Server is full (20/20). VAC authentication required.`。Go 的关闭方法直接关闭 UDP socket，正常断开无需发送这个拒绝帧。

**互操作边界。** 双向分别从序号 1 验证解密与标签，覆盖零载荷、非零随机填充、无填充、关闭整形后的 `01` 帧、FEC 分片、重复包、乱序差 63/64 和序号零。先送标签无效的帧，再送同序号的有效帧，后者应可接收。单测另构造认证有效但内长越界的包，验证其不交付 KCP。参考测试覆盖同向正常包、重复、外头篡改和小范围乱序。原测试中发包均为客户端至服务端，需要补测反方向。

## 3. KCP 与 FEC

在原生 sing-box 路径中，发送顺序为 smux 字节流 → KCP 段 → 可选 FEC 分片 → 自定义加密数据报 → UDP。KCP 的 `BlockCrypt` 是 `nil`，因此 KCP 层的加密、nonce、CRC 合计 0 B。每个数据分片和每个校验分片独立经过外层封装。以下偏移均从本层起始位置按 0 计。来源为 `pkg/cs2world/outbound.go:128–145`、`pkg/cs2world/inbound.go:98–105,130–139`、`pkg/transport/packet_conn.go:286–305`、`kcp-go/v5@v5.7.6/sess.go:228–251,770–787`。

### 3.1 KCP 段和 MTU

| 偏移 | 宽度 | 字段与表示 | Rust 收发约定 |
|---|---:|---|---|
| 0 | 4 | `conv`，u32 LE | 客户端随机选取，服务端从 KCP 段读取。与外层握手分配的连接 ID 分别存储。 |
| 4 | 1 | `cmd` | `0x51` PUSH，`0x52` ACK，`0x53` WASK，`0x54` WINS。 |
| 5 | 1 | `frg` | 本项目发送流模式 PUSH 时置 0。业务报边界由上层恢复。 |
| 6 | 2 | `wnd`，u16 LE | 广告接收窗口，单位为段。 |
| 8 | 4 | `ts`，u32 LE | KCP 毫秒时钟，在 ACK 中回送以供估算 RTT。 |
| 12 | 4 | `sn`，u32 LE | 段序号，ACK 引用相应 PUSH 的序号。 |
| 16 | 4 | `una`，u32 LE | 下一个期待接收的序号，确认其之前的各段。 |
| 20 | 4 | `len`，u32 LE | 随后段体的字节数。控制段通常为 0。 |
| 24 | `len` | 段体 | PUSH 携带连续的 smux 字节。从剩余输入继续读取下一段。 |

例如取 `conv=0x11223344, cmd=PUSH, frg=0, wnd=1024, ts=1, sn=0, una=0`，段体为 `61 62 63`，整个 27 B 段为 `44 33 22 11 51 00 00 04 01 00 00 00 00 00 00 00 00 00 00 00 03 00 00 00 61 62 63`。这是段格式示例。真实 smux 会话还需要流控制帧与流头。

Rust 应以 `from_le_bytes` / `to_le_bytes` 编解码。KCP 的序号与毫秒时钟比较使用 `later.wrapping_sub(earlier) as i32`。一次 KCP flush 可能把多个段合在同一个数据报，单个 smux 帧也可跨多个 KCP 段。Go 检查 `conv`、命令和段体长度，接收循环仅在至少剩余 24 B 时解析下一段。维护远端窗口及采样 RTT 时，Go 区分直接到达的包与 FEC 恢复包。来源为 `kcp-go/v5@v5.7.6/kcp.go:40–57,115–116,137–148,396–443,605–649,705–709,1015–1020`、`sess.go:1296–1366,1654–1667`。

### 3.2 FEC 分片、矩阵与接收状态

记数据片数为 `d`，校验片数为 `p`，总数为 `g=d+p`。示例配置显式使用 `10+3`。Go 原生选项在配置缺省时保留 `0+0`。任一数值 ≤0 时本端发送器关闭 FEC，向外层交付原始 KCP 报。适配目标使用双方接收器支持的 `g≤256`。接收器在启动时显式拒绝更大的总数，发送器另行调用 Reed–Solomon 构造函数，双方参数应在共同支持的范围内校验。来源为 `configs/cs2world_client.json:21–26`、`configs/cs2world_server.json:13–18`、`pkg/cs2world/options.go:11–28`、`kcp-go/v5@v5.7.6/fec.go:135–156,383–399`。

| 分片 | 0..3 | 4..5 | 6..末尾 | Rust 实现及示例 |
|---|---|---|---|---|
| 数据 | `seqid:u32 LE` | `f1 00` | `size:u16 LE`，随后是 KCP 输出字节。`size=2+KCP输出长度`。 | 例如组 0 的首个数据片包着上面的 27 B 段，前缀为 `00 00 00 00 f1 00 1d 00`，共 35 B。仅在运算用分片副本的尾部补零，原始数据片按实际长度发送。 |
| 校验 | `seqid:u32 LE` | `f2 00` | 从偏移 6 起全部是编码符号，包含对数据片 size 两字节的编码。 | 默认首组的第一校验片前缀是 `0a 00 00 00 f2 00`。每个校验报长度等于组内最长的完整数据报。 |
| 库预留 OOB | 固定 `ff ff ff ff` | `f3 00` | 编码器写 size，之后为 `convLE32` 与 OOB 内容。 | 本项目原生业务使用 KCP/smux 路径。OOB 是库的独立分支，不加入业务 UDP 的编码。 |

**发送分组。** 每方向独立从序号 0 开始。序号槽位为 `seqid % g`，组号为 `seqid / g`。槽位 `0..d−1` 为数据，其余为校验。组满才计算校验，最后一个数据片与前一个数据片的发送处理时间差达到 500 ms 时可跳过整组校验，序号仍前移 `p` 个槽。发送序号按 `paws=(u32::MAX / g) * g` 取模，默认 10+3 得 `paws=4294967287`，最后有效序号为 4294967286，随后从 0 开始。每个真实或校验报通过外层独立封装，此处的 `seqid` 与 KCP 的 `sn`、外层加密序号各自计数。来源为 `kcp-go/v5@v5.7.6/sess.go:90–93,770–779`、`fec.go:383–406,412–492,495–523`。

**校验计算。** 对 `d+p≤256` 的缺省路线，`klauspost/reedsolomon@v1.14.2` 使用 GF(2⁸)，约简多项式 `0x11d`。令 `V[r,c]=r^c`（域内运算，行列从 0 起），生成矩阵为 `V × inverse(V[0:d,0:d])`。前 d 行为单位阵，后 p 行按行号依次生成校验片。每个数据向量从数据片偏移 6 的 size 字段起，按组内最长向量右侧补零。Rust 选库时需要按实际字节核验矩阵、行序及填充。源码见 `reedsolomon@v1.14.2/reedsolomon.go:259–282,452–475,491–519`、`matrix.go:270–279`、`galois.go:26`、`options.go:46–50,64–70` 及 `kcp-go/v5@v5.7.6/fec.go:465–491`。

**校验字节例。** 这组输入用于单测 FEC 层。对 `i=0..9`，令数据区为 `LE16(3+i)` 后接 `i+1` 个值为 `i+1` 的字节，右侧补零至 12 B。用本机锁定的 Go 库实际编码得到以下三个 12 B 符号区。拼成分片时在每行前另加相应 seqid 与类型的 6 B。示例输入没有承载完整 KCP 段。

| 校验槽 | 偏移 6 开始的 12 B，十六进制 |
|---|---|
| 10 | `8e 00 45 c4 f5 19 c3 7e dc 1c 0f 14` |
| 11 | `3d 00 f2 64 7b ae 28 db 0d af 0c 1e` |
| 12 | `f9 00 12 ad 1c ba 92 8c f3 d4 05 28` |

**收包与恢复。** 读取偏移 4 的 u16 LE 分类。裸 KCP 直接输入。原始数据片把 `packet[8:]` 当常规输入立即交给 KCP，同时交给 FEC 缓存。校验片只参加恢复。在已收到至少 d 个不同分片且缺失数据时，按槽位重建，恢复片从开头取 `size`，检查 `2≤size≤已恢复分片长度` 后仅把 `recovered[2:size]` 作为恢复输入交给 KCP。空会话的首个校验片没有可提取的 conv，不能独立创建接收会话。在已有会话上收到 FEC 而本端没有解码器时，Go 懒建 `1+1` 解码器，按 data/parity 标志与序号槽位的匹配关系检测新比例。检测使用最多 258 个样本。确认合法的新 `d,p` 后清空旧组缓存再重建矩阵。自适应只改变接收侧，协议没有 FEC 配置协商帧。来源为 `kcp-go/v5@v5.7.6/sess.go:1088–1148,1166–1179,1296–1345`、`fec.go:161–225,233–259,289–334`、`autotune.go:29–55,107–149`。

## 4. smux 与目标地址

原生客户端在一个 KCP 字节流上创建并复用 smux 会话。每条 TCP 连接或 UoT 关联占一条子流，服务端从该流的开头读目标地址，再交给 sing-box 路由。独立的 `cmd/cs2-ghost` 固定目标 TCP 转发器不使用这里的目标地址前缀。来源为 `pkg/cs2world/outbound.go:97–109,134–152,155–185`、`pkg/cs2world/inbound.go:136–171`、`cmd/cs2-ghost/main.go:150–174`。

Go 的 KCP listener 按 UDP 源地址登记会话。已有地址携带不同 `conv` 时，`sn != 0` 会丢弃，`sn == 0` 可关闭旧会话再建立新会话。同一服务端地址上并行排空旧隧道与建立新隧道时，Rust 客户端须以不同本地 UDP 端口建会话。GNS 可在认证后登记新源地址，完整的 KCP/smux 流连续性仍受 listener 的地址键约束。FEC 恢复缓存淘汰比最新组落后三个组间隔以上的旧组。参见 `kcp-go/v5@v5.7.6/sess.go:1287–1366`、`fec.go:343–352`。

### 4.1 smux v1

| 偏移 | 宽度 | 字段 | Rust 行为 |
|---|---:|---|---|
| 0 | 1 | 版本 `01` | 接收时核对配置版本。 |
| 1 | 1 | 命令 `00 SYN, 01 FIN, 02 PSH, 03 NOP` | SYN/FIN/NOP 的长度必须为 0。UPD=`04` 是 v2 控制命令，v1 接收为协议错误。 |
| 2 | 2 | `len:u16 LE` | 仅计帧体。项目发送单个 PSH 帧体最多 32768 B。Go 接收按头中完整 u16 读取（可达 65535 B），零长 PSH 被忽略。 |
| 4 | 4 | `sid:u32 LE` | 客户端首个主动开流 SID 为 3，接着 5、7。服务端首个主动开流 SID 为 2，接着 4、6。主动分配器先加 2，溢出前停止开流。Keepalive NOP 使用 SID 0。 |
| 8 | `len` | 帧体 | 对底层流使用 `read_exact`，跨 KCP 段读满后再按 SID 投递。对未知 SID 的 PSH 仍须消费其帧体，以保持同步。 |

客户端开第一流的完整 SYN 为 `01 00 00 00 03 00 00 00`。同流写 3 B 数据 `abc` 时，单个 PSH 为 `01 02 03 00 03 00 00 00 61 62 63`。FIN 为 `01 01 00 00 03 00 00 00`。本项目定时 NOP 为 `01 03 00 00 00 00 00 00`。

接到 FIN 只标记对端写方向结束。接收端先交付已经缓存的数据，再给读者 EOF，另一个方向仍可发送。Go 的 `CloseWrite` 发送 FIN，显式 `Close` 也可发送同样的 FIN。Rust 需按发送顺序排在此前的 PSH 之后。接收器忽略已登记 SID 的重复 SYN，对已有流的重复 FIN 幂等，读完并丢弃该 SID 在 FIN 之后到达的 PSH。Keepalive 配置为间隔 15 s、超时检查周期 45 s，v1 接收背压由 4 MiB 会话共享预算控制。适配器也填了 `MaxStreamBuffer=1 MiB`，该逐流窗口只在 v2 生效。在 v1 暂停读取单流、累计超过 1 MiB 后恢复读取，应完整交付数据。共享预算耗尽时 Go 暂停读，超时检查也考虑这项本地背压。来源为 `pkg/cs2world/inbound.go:54–61`、`smux@v1.5.60/mux.go:34–67`、`frame.go:32–58,75–94`、`session.go:164–197,219,468–588,595–608`、`stream.go:562–590,680–699,704–733,848–877`。

### 4.2 标准目标地址与 UoT 的两套地址类型

两种地址编码都先发类型与地址，最后发 BE 端口。域名长度按编码后的字节计，1 B 长度允许至多 255 B。标准地址用于每条新流的首目标和 UoT v2 的请求目的地。UoT 地址用于未绑定模式中每个业务报的目标或来源。来源为 `sing@5dc452e537bf/common/metadata/socksaddr.go:3–7`、`common/metadata/serializer.go:50–75,78–94,101–112,131–169,212–222`、`common/uot/protocol.go:19–23,41–64`。

| 地址 | 标准类型 | UoT 逐报类型 | 类型之后的字节 | 总长及数值例（端口 53） |
|---|---|---|---|---|
| IPv4 | `01` | `00` | 4 B 原始网络顺序地址 + u16 BE 端口 | 7 B。标准 `192.0.2.1:53` 为 `01 c0 00 02 01 00 35`。 |
| IPv6 | `04` | `01` | 16 B 原始网络顺序地址 + u16 BE 端口 | 19 B。标准 `[::1]:53` 为 `04`，后接 15 个 `00`、`01 00 35`。 |
| 域名 | `03` | `02` | u8 长度 n + n B 域名 + u16 BE 端口 | `4+n` B。`a.test:53` 的 UoT 逐报地址为 `02 06 61 2e 74 65 73 74 00 35`。 |

普通 TCP 子流只在客户端→服务端开头写一次标准 AddrPort，然后双向传递原始业务字节。该地址是 smux 流内容，可以跨帧分割。Go 服务端读到地址后直接调用路由，协议没有成功响应字节。来源为 `pkg/cs2world/outbound.go:160–174`、`pkg/cs2world/inbound.go:155–171`。

### 4.3 UoT v2 与 legacy 入站

## 5. A2S 查询与探针

Go 入站在同一 UDP 端口先识别 A2S，再处理握手和加密数据。服务端始终创建 A2S 应答器，省略 `a2s` 配置时采用内建值。下表的 `H` 表示四字节 `FF FF FF FF`。分流要求至少 5 字节，`H` 后的单字节决定应答。标为 `zstr` 的字段是原始字符串字节后接一个 `00`。[服务端分流](../../../pkg/transport/packet_conn.go#L189) · [查询类型与分派](../../../pkg/a2s/responder.go#L81)

| 请求 | Go 服务端返回 | 解析注意事项 |
| --- | --- | --- |
| INFO，`H 54`。Win32 发 `H 54` + ASCII `Source Engine Query` + `00`，合计 25 B | 直接返回 `H 49` + INFO 正文 | Go 只检查类型，忽略请求的字符串与尾部。Win32 只处理直接 INFO 应答。 |
| PLAYER，`H 55 FF FF FF FF` | `H 41` + 随机 `u32LE`，共 9 B | Go 检查偏移 5–8 是否全部为 `FF`。 |
| PLAYER，`H 55` 后为其他值，或总长度小于 9 B | `H 44` + PLAYER 正文 | 常规二次查询复用刚获得的四个挑战字节。Go 不保存挑战号，也不校验二次查询是否匹配。 |
| RULES，`H 56`，或其他 A2S 类型 | 同一格式的 9 B challenge | 带回挑战后仍只返回 challenge。该版本未生成 RULES 列表。 |

**INFO 正文按以下顺序排列。** `11 | server_name:zstr | map:zstr | "csgo":zstr | "Counter-Strike 2":zstr | DA 02 | players:u8 | max_players:u8 | 00 | 64 | 6C | 00 | 01 | game_version:zstr | 00`。其中 `11` 为十六进制的协议版本 17，`DA 02` 为 AppID 730 的小端表示。最大人数后的五字节依次为机器人数量 0、专用服务器 `d`、Linux `l`、公开、启用 VAC。末尾扩展标记 EDF 为 0，无额外字段。Linux 和 VAC 均为固定返回值。[INFO 编码](../../../pkg/a2s/responder.go#L148)

**PLAYER 正文**先给出实际条数 `count:u8`，随后每个条目为 `index:u8 | name:zstr | score:i32LE | seconds_online:f32LE`，下标从 0 起。构造应答器时从 18 个预设名字中生成名单，初始分数为 2–29，初始在线时长为 120–2519 秒，之后时长随时间递增。INFO 的人数按进程本地小时重新计算，PLAYER 通常沿用起始名单，因此跨小时查询的两处人数可能不同。地图自进程启动起按配置顺序轮换。[人数与地图](../../../pkg/a2s/responder.go#L112) · [PLAYER 与 challenge 编码](../../../pkg/a2s/responder.go#L192)

| 服务端 A2S 配置 | 省略时的值 |
| --- | --- |
| `server_name` | `[Asia/HK] CS2 5v5 Competitive Practice #3 \| 128Tick` |
| `maps` | `de_mirage`、`de_inferno`、`de_dust2`、`de_ancient`、`de_nuke` |

| `fastdl_chunk_size` | 1248 | 1248 | 1248 | FastDL 分支常用目标总长。 |

数值参数小于或等于 0 时使用 Go 缺省。每个方向自行选包长，无需协商或匹配随机样本。KCP 的 15 ms 更新参数在另一路径固定赋值，与 `tick_rate_hz`、46 ms 心跳各自独立。[状态机配置](../../../pkg/shaper/state_machine.go#L13) · [客户端模板](../../../configs/cs2world_client.json#L28) · [服务端模板](../../../configs/cs2world_server.json#L33) · [Win32 缺省](../../../win32-xp/src/models.rs#L33) · [KCP 调优](../../../pkg/cs2world/inbound.go#L64)

设 `L` 为传给 `WriteTo` 的真实数据长度（包含已经加上的 KCP 或 FEC 开销），`M = L + 28`（外头 9 B、加密内头 3 B、GCM tag 16 B）。下表的长度是 UDP payload 字节数。每次真实发送先刷新最后写入时间，距窗口起点超过 250 ms 才清零累计字节数，再计入本包。窗口为按需重置的累计窗口。[状态转换及抽样](../../../pkg/shaper/state_machine.go#L75) · [最终包长](../../../pkg/protocol/gns.go#L352)

| 条件 | 加密内层 mode | 总长计算 |
| --- | --- | --- |
| 关闭整形，真实数据 | `01` Combat | `M`。 |
| 开启整形，`L ≤ 480` 且本窗口累计 `≤ 6000` | `01` Combat | 抽样并取整，均值为配置值，标准差为 38 B。若结果低于 `M`，改用 `M + U[0,35]`。 |
| 开启整形，`L > 480` 或计入本包后累计 `> 6000` | `02` FastDL | 若 `M > fastdl_chunk_size` 则取 `M`。否则以 85% 概率取配置的块长，其余取 `M + U[0,63]`。 |
| 客户端允许发空心跳 | `00` Idle | 真实载荷长度 0。以 72 B 为均值、10 B 为标准差抽样取整，截到闭区间 54–108 B。 |
| 休眠 | 无 | 跳过该次心跳。下一次真实写入立即恢复状态计算。 |

`U[a,b]` 表示端点均包含的均匀随机整数。封装时目标总长至少为 `M`。当 `M ≤ 1380` 时目标最长为 1380 B；若真实数据加开销已经更大，封装保留数据所需长度。填充字节位于密文中。接收端对 mode 为 `00` 或真实长度为零的包计数并吞掉，其他非空真实载荷交给 KCP。[封装与填充](../../../pkg/protocol/gns.go#L352) · [接收过滤](../../../pkg/transport/packet_conn.go#L264)

**三个时钟。** 客户端的空包循环每 46 ms 检查一次，约 21.7 次/秒；距上次真实传输层写入小于 35 ms 时跳过，超过 `idle_sleep_seconds` 时进入 Sleep，恰好等于阈值时仍可发送。发空包本身不刷新该计时。smux 的保活间隔另设为 15 秒、超时 45 秒；健康会话的 NOP 也会经 KCP 触发真实写入。即使应用持续空闲，底层仍可能持续刷新计时。服务器端每 60 秒清理空闲超过 900 秒的会话，这是另一项生命周期检查。[心跳与会话清理](../../../pkg/transport/packet_conn.go#L126) · [Idle/Sleep 判定](../../../pkg/shaper/state_machine.go#L106) · [smux 保活配置](../../../pkg/cs2world/inbound.go#L54)

**Go 与 Rust 互测（待执行）。** 在已知载荷长度的 Go/Rust 交叉发送中分别验证关整形、`L=480/481`、窗口累计恰好 6000/超过 6000、FastDL 目标长度和加密后还原的原始载荷。随机包长使用范围或多次采样断言，不逐包比较随机字节。单独驱动状态机检查 35 ms 和 Sleep 边界，再在已建立的真实会话中区分空包、TCP 应用流量与 smux NOP；以解密后的 mode/载荷和实际 UDP 长度作为观测量。把 `tick_rate_hz` 分别设为不同值，在 Go 参考客户端验证其空包检查节拍仍为 46 ms，实测间隔须允许操作系统调度抖动。现有 Go 测试检验封装、解密和重放，整形统计与这些计时边界需另行覆盖。[Go 编解码测试](../../../pkg/protocol/gns_test.go#L53) · [客户端实际定时器](../../../pkg/transport/packet_conn.go#L151)

## 7. 分享链接与配置来源

`cs2world://<百分号编码的PSK>@<host>:<port>?<有序查询>#<百分号编码的备注>`。编码器输出显式端口，解析时省略端口取 27015；IPv6 字面值用方括号，节点对象中去括号。PSK 来自 userinfo 的用户名部分，PSK 内的 `@`、`:`、`#` 等分隔符需要编码。先按 URI 拆字段，再对用户名和备注作一次 UTF-8 百分号解码并 trim。`+` 在用户名或 fragment 中表示字面加号，查询键值按表单规则解码。无备注时解析器生成 `cs2world_{host}:{port}`；本地节点 ID 与探针结果不写入链接。[Python 工具](../../../scripts/cs2world-link.py) · [Win32 URI](../../../win32-xp/src/uri.rs) · [节点模型](../../../win32-xp/src/models.rs)

| 编码顺序、短键 | 接受的别名（短键优先） | 链接默认 | Win32 数字下限 |
|---|---|---:|---:|
| `ds` | `data_shards` | 10 | 0 |
| `ps` | `parity_shards` | 3 | 0 |
| `mtu` | 同名 | 1180 | 256 |
| `sw` / `rw` | `snd_wnd` / `rcv_wnd` | 1024 / 1024 | 16 / 16 |
| `shaper` | `shaper_enabled` | true | 布尔 |
| `tick` | `tick_hz`、`tick_rate_hz` | 64 | 1 |
| `sleep` | `idle_sleep`、`idle_sleep_seconds` | 600 | 1 |
| `combat` | `combat_bytes`、`combat_mean_bytes` | 180 | 64 |
| `fastdl` | `fastdl_chunk`、`fastdl_chunk_size` | 1248 | 256 |

两个编码器按表顺序输出与链接缺省不同的查询项。布尔输出 `1/0`，输入接受 `1,true,yes,on` 及 `0,false,no,off`，值忽略大小写及两端空白。Python 可从完整 JSON 的 `outbounds` 选首个 `type="cs2world"`，也可读单个 outbound。其编码函数仅检查配置中存在的 KCP/shaper 键；直接对省略这两个对象的 Go JSON 调用旧工具会生成带链接缺省语义的 URI。新核心从已解析且已补好**来源默认值**的节点导出，例如把 Go 的 FEC 关闭、整形关闭明确编码为 `ds=0&ps=0&shaper=0`（其他非链接缺省值也照实编码）。

| 两份旧实现存在的差异 | Rust 拟采用的可测契约 |
|---|---|
| Python `quote(safe="")` 保留 `-._~`；Win32 `NON_ALPHANUMERIC` 将其写成 `%2D%2E%5F%7E`。Python 可取 tag 或自动生成 fragment；Win32 可省略空名 fragment。 | 同一逻辑对象支持两种明确的导出形式。新分享默认 Python 规范形式；原 GUI 的“复制链接”保持 Win32 拼写并测字节相等；两种链接均可交叉导入。 |
| Python `parse_qs` 键名区分大小写、每个键取首个非空值；Win32 键名转小写、同键后值覆盖。Python 接受有符号整数；Win32 要求 `u32` 与表中下限，非法时按别名优先顺序尝试或回落。 | 测试数据区分 Python 与 Win32 的解析策略；GUI 批量导入按原行为，CLI 的兼容入口按 Python。标准导出的链接只写唯一短键。运行时配置校验对解析结果独立执行，越界时给出字段和原因。 |
| Python 的 `parsed.port or 27015` 使显式 `:0` 也回落为 27015，Win32 拒绝显式端口 0。Python 的 `.hostname` 通常将主机名折叠为小写；Win32 使用 `Url` 对自定义 scheme 的 host 表示。 | 正常链接在两边语义一致；保留历史输入测试，核心持有原始名称及路由比较用规范化视图。新导出始终写有效端口。 |
| Win32 批量导入接受多行、标准或 URL-safe Base64，有/无 padding，剔除空白。原文没有协议前缀时才尝试整体解码，长度至少 12，包含前缀的行再逐条解析。 | GUI 保留逐行忽略坏记录的行为，额外返回成功/失败计数便于显示。Python 单 URI 入口保持单条语义。 |

**可核验样例。** 节点 PSK 为 `p@ss-._~`，地址为 `[2001:db8::1]:27016`，FEC 4:1、整形关闭、备注 `HK Lab`。其余字段取链接默认。阶段 0 实调 Python 脚本和本地未修改的 Win32 `models.rs`、`uri.rs`。两边均接受这两个输入，均还原同一节点，并分别重编码为下列精确字符串。Win32 还通过重复键取末项、键名折叠和拒绝端口 0 的断言。

```text
Python: cs2world://p%40ss-._~@[2001:db8::1]:27016?ds=4&ps=1&shaper=0#HK%20Lab
Win32:  cs2world://p%40ss%2D%2E%5F%7E@[2001:db8::1]:27016?ds=4&ps=1&shaper=0#HK%20Lab
```

**无法无损分享的配置。** 配置中的 PSK 允许首尾空白，两个旧 URI 导入器都会 trim。对这类配置，Rust 继续使用原始 PSK 连接；导出链接时返回不含密钥值的可读错误，并允许使用原 JSON 迁移。对包含首尾空白的纯测试 PSK，分别验证 JSON 握手、阻止有损导出与旧 URI 的实际解析结果。

阶段 1 的链接语料应包含两种拼写、非 ASCII PSK/备注、默认端口、缺 fragment、未知键、别名、显式关闭、重复键、端口 0、越界值、IPv6、含好坏记录的多行/Base64 输入。对规范输入测“旧编码 → 新解码”和“新编码 → 两个旧解码”，对有分歧的输入分别记录旧行为。协议分层、构建产物与测试矩阵见[阶段 0 设计](2026-11-21-cs2world-core-design.md)。
